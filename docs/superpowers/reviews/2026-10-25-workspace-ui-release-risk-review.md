## 本次新增的已确认问题

### R1 · P2：改密成功绕过笔记的未保存保护

位置：[WorkspaceAccountDialogs.tsx:94](../../../frontend/src/app/profile/components/WorkspaceAccountDialogs.tsx#L94)、[WorkspaceShell.tsx:111](../../../frontend/src/components/workspace/WorkspaceShell.tsx#L111)。

触发：编辑笔记并留有未保存内容 → 打开设置/账户/修改密码 → 提交成功。1.5 秒后直接调用 `logout()`，未经过工作区 `requestAction`，没有应用内的保存/放弃/继续编辑选择。`auth.ts:56` 在导航前清除 token/user。

影响：浏览器仍可能弹出原生离页警告；若选择留页，凭据已经清除，草稿也无法照常保存；若离开，内存中的编辑可能丢失。不能描述为一定没有浏览器警告，也不能认为原生警告解决了问题。

归因：旧改密入口仅在个人页；本次上下文设置可以覆盖仍挂载的笔记编辑器，新增了跨模块退出路径。普通账户退出已接入 `requestAction(logout)`，改密退出漏接。定向真实组件用例确认 logout 一次、save/discard 均零次、应用保护弹窗未打开。

建议：在打开改密表单或提交请求前，先通过统一编辑保护解决后台笔记草稿；不要等服务端改密成功后才决定如何保存。此项应优先处理。

### R2 · P2：改密成功后的重新登录要求可以被卸载取消

位置：[WorkspaceAccountDialogs.tsx:53](../../../frontend/src/app/profile/components/WorkspaceAccountDialogs.tsx#L53)，以及第 95、99 行。

触发：无脏笔记时改密成功，在 1.5 秒内浏览器后退到 `/auth`，工作区与表单卸载。清理函数取消唯一的 logout 定时器。若请求发出后、返回前离开，`active` 判断也会跳过成功后的退出。

影响：token/user 留存。后端现有改密逻辑只更新密码，没有撤销原 JWT；因此“成功后需要重新登录”的原有合同没有兑现。这里并非声称新引入了 JWT 的全部安全问题。

归因：旧个人页定时器不随组件卸载取消；本次共享表单的清理把业务后续动作一同取消。受控用例确认成功后卸载再推进时间，logout 为零次。

建议：将成功后的会话清理交给不依赖表单存活的层；同时核对请求发起时的身份/token，防止迟到的 A 账号结果清掉后来登录的 B 账号。

### R3 · P2：历史接口一次失败会卡住新建笔记对话，页面内无法重试

位置：[chat/page.tsx:102](../../../frontend/src/app/chat/page.tsx#L102)、第 236 行；[useChatSession.ts:156](../../../frontend/src/hooks/useChatSession.ts#L156)。

触发：笔记页成功创建空绑定会话 → 进入 `/chat?session=新ID` → 第一次历史 GET 返回 503。新会话不在本地缓存；hook 在失败时也设置 `sessionsLoaded=true`，页面据此完成“不存在/无法读取”的一次性判断，并设置 `entryError`。

影响：网络恢复后，点击发送仍被错误门禁挡住；没有重新加载历史，也没有重试按钮。刷新/重新进入才能恢复指定会话。数据未被删除，但本次新增的笔记→对话入口被故障卡住。页面“请重试”的文案与可用动作不符。

归因：一次性历史读取是旧实现；显式会话入口、错误门禁与新建绑定跳转是本次新增。定向用例恢复 mock 后再次发送并推进 5 秒，GET 仍只有一次、聊天 POST 为零。

建议：区分“加载失败”和“加载成功但不存在”，提供真实重试，并允许重试成功后重新校验显式会话；可考虑把已确认保存的会话交接给聊天缓存，但仍需服务端校验。

### R4 · P2：删除的迟到响应会把用户拉回笔记列表

位置：[notes/page.tsx:246](../../../frontend/src/app/notes/page.tsx#L246)。

触发：确认删除笔记 → 请求仍在进行时浏览器后退到聊天/个人页 → 旧删除请求成功。闭包未检查挂载、路由或操作归属，仍调用 `go('/notes')`。

影响：新页面的阅读或填写被抢走导航。原笔记页面卸载并不能阻止跨页仍存活的公共导航函数。尚未将此断言扩写为消息一定丢失。

归因：基线删除成功只更新本地状态，没有这次新增的路由跳转。真实 NotesPage 受控用例在卸载后 resolve 删除 Promise，仍观察到 `push('/notes', {scroll:false})`。

建议：删除成功可以更新缓存，但只有发起操作的用户/页面会话仍有效、且仍查看被删笔记时才执行返回列表；旧响应不应决定新页面导航。

### R5 · P2：部分历史 Markdown 的阅读格式退化

位置：[NoteWorkspaceReader.tsx:17](../../../frontend/src/app/notes/components/NoteWorkspaceReader.tsx#L17) 至第 24 行。

触发：历史笔记无 `contentJson`，正文是合法的 Markdown 缩进代码块，例如 `代码示例\n\n    const existing = 1;`。有限语法正则未命中，阅读器把它当作普通文本 JSON。

影响：旧阅读器可显示的代码块，在新阅读页失去代码格式和语义。这里只确认阅读退化，没有证据证明源数据被写坏。类似参考式链接/Setext 标题也存在规则覆盖缺口，未按另一项重复计数。

归因：旧卡片将历史字符串交给原有 Markdown 阅读器；新 Reader 增加启发式分流。相同正文用既有 Viewer 生成 `pre code`，新 Reader 不生成，已复现。

建议：保留完整的历史 Markdown 解析合同，通过解析器处理换行，避免用语法子集正则决定是否解析 Markdown。补充历史格式兼容用例。

### R6 · P2：笔记开场的旧错误覆盖后续普通对话状态

位置：[chat/page.tsx:85](../../../frontend/src/app/chat/page.tsx#L85)、第 234、277 行。

触发：“从这条笔记聊起”保存失败，例如来源已删除；随后直接输入普通问题，并成功收到 committed 回答。普通发送没有清除独立的 `careError`。

影响：成功回答仍显示“未能开始笔记对话”；因错误选择顺序是 `entryError || careError || streamError`，旧错误还会遮蔽后续普通请求的真实失败。未确认消息持久化损坏。

归因：基线共用流错误，正常发送会清除；本次拆分开场错误后漏掉清理。相同复现用旧页面成功后无 alert；当前页面的该预期失败，实际同时出现成功回答和旧 alert。

建议：接受普通发送时清理已结束的开场错误，或按操作/会话限定其展示归属。

## 非阻塞小问题

P3：已有笔记进入编辑后没有任何修改，仍启用的“保存”点击后无反馈，也不返回阅读。[NoteWorkspaceEditor.tsx:83](../../../frontend/src/app/notes/components/NoteWorkspaceEditor.tsx#L83) 只在 save 返回 true 时退出，而 [useNoteEditor.ts:208](../../../frontend/src/app/notes/hooks/useNoteEditor.ts#L208) 的无变更分支返回 false。建议禁用干净状态保存，或让其明确完成退出；受控用例已确认。

## 提交与发布还需核清的范围

这部分是发布前置条件，不混算为上述 UI 新增缺陷。

1. **不能直接把全部未提交文件作为 UI 发布提交。** 当前 Git 有 114 个已跟踪变更文件、284 个未跟踪文件；后端占 51 个已跟踪变更和 19 个未跟踪文件。它们包含迁移之前的功能，不能宣称全部受此次 UI 验收覆盖，也不能为了拆提交而遗漏新 UI 依赖的旧工作。
2. **前后端版本配对未与线上实际版本核对。** 例如新入口依赖服务端 `sourceNoteId` 保存/恢复；工作区后端支持，但当前 HEAD `3ce3847` 中的 chat schema/service 不支持。只发布前端到旧后端可能变成普通会话、丢失笔记绑定语义。这里未断言线上正在运行该 HEAD；实际线上 commit/镜像尚未读取。必须先确定发布基础版本与所需配套改动。
3. **现有部署指南不是这次 UI 发布单。** [DEPLOY_GUIDE.md:20](../../../deploy/DEPLOY_GUIDE.md#L20) 仍指定旧后台发布分支，包含 owner 初始化等旧流程，不能原样当作本次上线操作。当前未形成针对本次准确 commit/镜像、前后端配对、验证项、回滚触发与旧镜像的发布记录。

建议顺序：修复上述问题并补定向回归 → 整理可审计的提交与配套依赖 → 用拟发布的准确版本在预发布环境验收旧笔记、保存冲突、登录、来源对话与故障恢复 → 记录现网版本和数据库备份、保留旧镜像，按现有部署能力分批切流并观察。代码回滚不应默认恢复数据库，以免抹去发布后用户的新笔记。本轮不实施发布基础设施，也未执行任何线上操作。
