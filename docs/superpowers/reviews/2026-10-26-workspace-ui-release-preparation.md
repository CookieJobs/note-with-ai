# NoteWithAI 工作区 UI 版本交付准备

日期：2026-10-26。本文记录 UI 修复交付时的准备边界。后续用户已授权提交、推送与上线，现网版本核对、完整后端测试和备份已完成，发布执行见 [本次发布计划](../plans/2026-10-26-workspace-ui-release.md)；以下原清单不是可直接照抄的生产指令。

## 准确的变更边界

当前分支为 `codex/workspace-ui-migration`，HEAD 为 `3ce3847`。工作区包含迁移前的未提交功能，不能用 HEAD→工作区的所有差异代表 UI 改版，也不能只摘取几个新页面而遗漏依赖。

| 层次 | 对照依据 | 用途 |
| --- | --- | --- |
| 迁移前的功能与未提交工作 | `baseline-start.json`、`baseline-status.txt` | 识别原本就存在的后端/认证/笔记协议等工作；需要另行核对其交付状态 |
| 已验收 UI 迁移 | `baseline-source.tar.gz` → 当前源码；迁移 Spec、S1/S2/S3 验收报告 | 全部新工作区及真实页面迁移 |
| 本轮发布前修复 | `release-fixes/pre-fix-source.tar.gz` → `release-fixes/final-fixes.diff` | 23 个源码/测试/README 文件，R1–R6 与 P3；不含后端或依赖版本修改 |

上述证据均在 `.superpowers/workspace-ui-migration/`。本轮 213 个源码文件与验收生产副本逐一一致。认证/后台页面和主稿未因本轮修复改动。暂不进行全量 `git add`、批量提交历史工作或从旧提交覆盖当前文件。

下一步整理 Git 时，先确认原有功能应属于哪个版本：可以按配套业务基础、UI 迁移、缺陷修复拆分可审阅提交；拆分后的**最终候选版本仍须完整构建与验收**。当前忽略目录中的夹具、凭据、日志、快照和构建副本不应进入产品提交。

## 必须匹配的后端合同

| 界面能力 | 当前本机依赖 | 发布前核对 |
| --- | --- | --- |
| 创建/编辑/冲突保护 | `/api/notes` 的 body、revision、`expectedRevision/changes`、标准笔记返回 | 线上是否支持该协议及历史笔记 revision；若带入未上线协议，先演练兼容/回填，不直接对生产执行脚本 |
| 未加载的来源笔记 | `GET /api/notes/:id` 按当前用户鉴权 | 来源可读、删除/无权/失败状态正确 |
| 笔记→对话 | `/api/chat/save` 接受并持久化 `sourceNoteId`，历史返回绑定，流返回 committed 与来源快照 | 不能配到不支持绑定的旧后端；旧 HEAD 中没有这些合同，不代表已确认线上版本如此 |
| 拟标题 | `/api/notes/title-suggestions` 与原有请求/额度校验 | 配套服务是否已经交付，失败不影响手动标题保存 |
| 灵感/设置 | inspirations 历史、用户状态、viewed、settings、unviewed-count | 两入口同一状态；主动发现 worker 不随 UI 发布顺便启用 |
| 个人/账户 | profile analysis、user stats、auth profile/password | 保持原账号验证和资料合同；本轮没有增加 JWT 全局撤销能力 |

UI 修复首次交付时尚未读取现网 commit、镜像和数据库状态；后续核对已确认生产基础与远端 main 一致，本次将按完整配套版本发布，不能宣称前端可独立发布。

- 若线上已具备所有合同：在同一后端版本上验证本次前端候选包，再决定是否只发布前端。
- 若线上缺少其中任意合同：先将必要业务改动纳入明确的配套版本，独立审查后端变更并执行相应测试，再安排兼容的发布顺序。UI 的 585 项前端测试不覆盖全部历史后端工作。

## 发布单与回滚准备

现有 `deploy/DEPLOY_GUIDE.md` 指向旧后台发布分支，并包含 owner 初始化等步骤；本次不得原样照抄。实际发布前填写以下记录，使用确认过的候选 commit/镜像，不从生产机器临时挑未提交文件。

| 项目 | 当前状态 |
| --- | --- |
| 候选 commit、前后端镜像及关联业务提交 | 待整理 Git 后确定 |
| 现网 commit、镜像、配置版本与前后端配对 | 待只读核对 |
| 与生产相同运行方式的预发布验收 | 待候选版本及环境明确后执行；本轮仅本机 production build/运行 |
| MongoDB 备份、恢复验证、旧镜像保留 | 待正式发布准备，不由本轮本机验收替代 |
| 分批切流方式、观察时间与责任人 | 按现有部署能力确定，不假设已有灰度平台 |
| 回滚入口与触发条件 | 发布单需明确：保存异常、权限异常、来源混淆应立即停止扩大流量并检查/回滚 |

预发布重点复验已有账号及旧笔记、真实保存与刷新、版本冲突、登录重定向、来源对话和历史故障恢复。运行时、API 代理、静态资源与构建资源限制按实际部署环境检查，不能把本机 Node 构建等同于目标容器/服务器已通过。

回滚优先恢复已保留且匹配的旧代码/镜像，保留用户发布后新增笔记。**不要把恢复数据库备份当作常规代码回滚动作**，否则会丢弃发布后新写入的数据；确需数据恢复时应单独评估。
