# NoteWithAI 前端体验基础治理设计 Spec

- 状态：待评审
- 日期：2026-09-09
- 范围：Web 前端视觉系统、响应式、无障碍与笔记页性能
- 依据：2026-09-09 Impeccable + Frontend Design 审计、`PRODUCT.md`
- 目标基线：WCAG 2.2 AA

## 1. 决策摘要

本 Spec 解决前端审计确认的全部 P1、P2 问题。实施完成后，NoteWithAI 不再表现为几套独立模板的组合，而是共享一套稳定的视觉语法，同时保留两个用户明确希望继续拥有的特征：

1. Profile 保留依据用户画像生成的动态氛围色，但氛围色只用于装饰性表达，不控制正文、操作和信息状态。
2. Auth 保留 Apple 式布局的简洁、克制与精细感，但不继续复制 Apple 的具体配色、阴影和品牌表达。

全站以 Inspiration、Memory、Publish 已形成的安静靛蓝风格为基础语言，使用共享的语义 Token、排版、圆角、边框、焦点、动效和响应式规则。动态个性建立在该基础之上，而不是替代基础。

实施顺序为：

1. 先修复影响使用和合规的 P1 问题。
2. 再建立共享 Token 与基础组件约束。
3. 随后迁移 Profile、Auth、Notes、Chat 等页面并解决 P2 性能问题。
4. 最后完成跨页面视觉、键盘、屏幕阅读器和性能验收。

本项目只有在第 12 节的完成定义全部满足后才算完成；不能以单个页面视觉更新代替整体收敛。

## 2. 与现有文档的关系

### 2.1 继续有效的文档

- `PRODUCT.md` 的产品定位、品牌人格、反例、设计原则和 WCAG 2.2 AA 基线继续有效。
- `2026-09-01-core-experience-loop-design.md` 中“捕捉、关联与回望”的产品闭环继续有效。
- `2026-05-17-auth-flow-design.md` 中登录、注册、验证码和重置密码的业务流程继续有效。
- `2026-05-24-profile-layout-redesign.md` 中账户资料、AI 画像、推荐和数据来源继续有效。

### 2.2 被本 Spec 覆盖的旧决策

- Auth Spec 中“保持现有 Apple 风格”的视觉决策，被“保留简洁结构、迁移到 NoteWithAI 视觉系统”取代。
- Profile Spec 中动态氛围色影响整页背景、彩色进度条、层层卡片和通用 AI Dashboard 表达的决策，被“受控氛围色”取代。
- 任何要求移动端继续把完整 Logo、三项主导航和账户入口挤在同一行的实现，均被新的响应式导航规范取代。
- 任何依赖 hover 才能发现核心关系入口或主要操作的实现，均被可见、可触控、可键盘操作的入口规范取代。

本 Spec 不重复定义认证、AI 画像或笔记关系的后端业务语义，只处理完成前端基础治理所必需的接口调整。

## 3. 背景与问题陈述

当前产品已经有三个值得保留的优势：

- Inspiration、Memory、Publish 页面形成了清晰、可信、克制的靛蓝视觉方向。
- 关键产品文案能够表达隐私边界、来源依据和用户控制权。
- 前端已有部分语义 Token、动态加载、状态反馈和可访问名称基础。

但这些优势没有形成全站约束。审计确认了以下系统性问题：

- 390px 视口下，主导航逐字换行，笔记标题被操作区挤成竖排。
- Memory 的主要确认按钮因 CSS 优先级变成白底白字。
- 用户菜单、推荐卡片、聊天历史等交互使用不可键盘操作的 `div`。
- 自制 Dialog、Drawer 缺少完整焦点和可访问状态管理。
- 多处正常字号文字对比度低于 4.5:1。
- `/notes` 首次加载约 421kB，一次渲染 251 条笔记，辅助技术树超过 6800 个节点。
- 页面大量硬编码颜色，同一产品出现灰白毛玻璃、靛蓝内容页、Apple Auth、彩色 AI Dashboard 等多套视觉语言。
- 项目存在大量 spring、blur、filter 和装饰动画，但没有 reduced-motion 处理。

这些问题同时影响产品可信度、移动记录效率、无障碍、长期维护成本和页面性能，不能继续用局部覆盖样式解决。

## 4. 目标与非目标

### 4.1 目标

- 修复第 5 节列出的全部 P1 问题。
- 修复第 6 节列出的全部 P2 问题。
- 建立可约束全站的语义设计 Token 和基础交互组件。
- 让 320px 以上的核心页面都能正常阅读和操作。
- 让主流程可以只用键盘完成，并兼容屏幕阅读器和 reduced-motion。
- 降低笔记页首屏 JavaScript、初始 DOM 和长列表交互成本。
- 统一全站视觉，同时保留 Profile 氛围色与 Auth 的简洁质感。
- 把“笔记之间的关系与记忆”作为品牌识别点，而不是依赖通用渐变、阴影或仪表盘装饰。

### 4.2 非目标

- 不改变注册、登录、验证码、密码重置的服务端流程。
- 不重新定义 AI 画像、推荐、Memory 或 Inspiration 的生成算法。
- 不新增社交网络、动态流、点赞、评论或公开用户主页。
- 不在本阶段实现完整的用户自选主题市场或任意配色编辑器。
- 不为了统一视觉而删除 Profile 动态氛围色或 Auth 的精细简洁布局。
- 不处理审计中的 P3 文案和低优先级装饰问题，除非它们在组件迁移中自然被解决。
- 不引入与本次治理无关的后端重构。

## 5. P1 修复范围

### 5.1 P1-1：共享移动导航重排

#### 当前问题

共享导航使用 `1fr auto 1fr` 三栏布局，移动端没有专用断点。完整 Logo、三项导航和账户入口在 390px 下争抢同一行，导航中文逐字换行。

#### 目标设计

- 桌面端保留居中的主导航和左右区域。
- 小于 768px 时改为两层结构：
  - 第一层：聊天菜单或页面上下文、短品牌标识、账户按钮。
  - 第二层：三项主导航，单行显示；空间不足时允许横向滚动，不允许文字断行。
- 导航容器不得产生页面级横向滚动。
- 当前页使用 `aria-current="page"`。
- Logo 使用普通链接或非标题文本；每个页面只保留一个内容 H1。
- 账户入口使用 `button`，包含 `aria-expanded` 和 `aria-controls`。
- 320、360、390、768、1024、1440px 均有明确布局行为。

#### 验收

- 320px 宽度、200% 浏览器缩放下，三个导航标签仍可辨认并可访问。
- 主导航、账户菜单和聊天菜单可完整使用键盘操作。
- 页面没有由共享导航造成的水平滚动或文字逐字排列。

### 5.2 P1-2：笔记卡片响应式与触控

#### 当前问题

笔记标题、日期、公开状态和多个操作按钮位于竞争宽度的同一行；移动端标题会被压成单字列。编辑、删除等按钮约 28px，关系入口视觉过弱并依赖 hover。

#### 目标设计

- 卡片结构固定为：内容标题与正文、元信息行、关系入口、操作区。
- 小于 650px 时，标题与元信息必须分行。
- 移动端只常驻一个最重要的上下文动作；编辑、公开、删除等低频动作进入“更多”菜单。
- 所有主要触控目标采用 44×44px 产品基线；WCAG 2.2 AA 的 24×24px 最低要求不能被误写成 44px，但本产品主动使用更宽裕目标。
- 关系入口不能只表现为卡片边缘细把手。必须显示一条可理解的关系提示或明确按钮，并支持触控、键盘和屏幕阅读器。
- hover 只能增强反馈，不能作为发现和使用功能的前提。

#### 验收

- 使用 40 个以上中文字符的标题，在 320px 下不出现单字竖排。
- 触控主操作之间没有误触风险。
- 不使用鼠标也能打开关系、编辑和删除入口。

### 5.3 P1-3：Memory 确认按钮可见性

#### 当前问题

`.actions button` 覆盖 `.confirm` 的背景，造成“这是准确的”按钮白底白字。

#### 目标设计

- 所有主按钮统一使用共享 `Button` 的 primary variant，不再由页面级选择器组合决定关键颜色。
- 页面局部规则不得覆盖按钮的语义前景色、背景色和边框状态。
- normal、hover、focus-visible、active、disabled、loading 均需要独立可辨认。

#### 验收

- Memory 主确认按钮在所有状态下满足文字 4.5:1、非文字控件边界 3:1。
- light、dark、系统高对比度模式下均能辨认。

### 5.4 P1-4：语义交互与键盘支持

#### 修复对象

- TopNavigation 用户菜单触发器。
- Profile 推荐条目。
- ChatHistoryPanel 会话条目和删除动作。
- Auth 密码显示/隐藏按钮。
- 其他扫描发现的 `div onClick`、`span onClick` 和只有 `title` 的图标按钮。

#### 规范

- 导航使用 `a`/`Link`，执行动作使用 `button`。
- 列表项内不得嵌套两个相互冲突的点击区域；会话打开与删除分别拥有独立语义。
- 图标按钮必须有稳定可访问名称。
- 所有交互状态有一致、清晰且不被裁切的 `:focus-visible`。
- 不通过正 tabindex 重排页面。

#### 验收

- 仅使用 Tab、Shift+Tab、Enter、Space、Escape 可以完成主导航、账户菜单、聊天会话、Profile 推荐、Auth 和 Memory 操作。
- 自动化检查不再发现无角色的点击元素。

### 5.5 P1-5：Dialog、Drawer 与焦点管理

#### 目标设计

- 建立共享 Dialog 和 Drawer 基础组件，统一处理：
  - `role="dialog"` 与 `aria-modal="true"`；
  - 标题和描述关联；
  - 打开后的初始焦点；
  - 焦点约束；
  - Escape 关闭；
  - 关闭后焦点归还；
  - 背景内容不可交互；
  - reduced-motion 下取消位移动画。
- 非模态的内联确认不得错误声明为 modal。
- Chat 移动抽屉关闭时必须卸载，或同时使用 `hidden`/`inert` 和正确的 `aria-hidden` 管理，不能只用 transform 移出屏幕。
- 删除等破坏性操作必须明确目标和后果，默认焦点不得落在破坏性按钮上。

#### 验收

- 屏幕阅读器在抽屉关闭时无法访问其中的会话列表。
- 打开任一模态后，Tab 不进入背景页面；关闭后返回原触发器。
- Escape 行为不会误删数据或清空草稿。

### 5.6 P1-6：颜色对比度与表单标签

#### 目标设计

- 正常尺寸正文、提示、时间、邮箱、占位符等文字对背景至少 4.5:1。
- 大号文字至少 3:1。
- 控件边界、焦点环和有意义图标至少 3:1。
- 不使用 placeholder 替代持久可见的 label。
- Auth 的邮箱、密码、新密码、验证码均有程序化关联的 label；错误提示与对应输入建立关联。
- 颜色不是表达 active、error、success、private/public 状态的唯一手段。

#### 验收

- 删除或替换审计确认失败的 `#9ca3af`、`#86868b`、`#718096`、`#a0aec0` 等组合，除非其背景和字号经过验证满足标准。
- 关键页面通过自动对比度扫描和人工合成背景复核。

## 6. P2 修复范围

### 6.1 P2-1：笔记页加载、DOM 与动画性能

#### 当前基线

- `/notes` 生产构建首次加载约 421kB。
- 当前测试账户一次渲染 251 条笔记。
- 页面辅助技术树超过 6800 个节点。
- 富文本编辑器在页面空闲约 1200ms 后预加载，即使用户没有表达记录或编辑意图。
- 整个列表使用 Framer Motion layout spring。

#### 目标架构

1. 笔记列表 API 支持基于稳定游标的分页，首批默认 30 条。
2. 关系抽屉接口直接返回需要展示的候选摘要，不再依赖前端 `allNotes.find` 或全量笔记列表。
3. 每张卡需要的 AI 偏好并入列表 DTO 或批量返回，禁止列表挂载后逐卡请求。
4. 列表使用渐进加载；在分页后仍超过性能预算时才加入虚拟化，避免不必要复杂度。
5. RichTextEditor 继续动态拆包，但取消固定空闲预加载；仅在 hover、focus、pointerdown、键盘快捷键或用户打开捕捉器等明确意图后预加载。
6. layout 动画只作用于新增、删除或重新排序的可见条目；reduced-motion 下关闭。
7. filter、backdrop-filter 和大面积模糊不得在滚动列表中持续动画。

#### 性能预算

- `/notes` 首次加载 JavaScript 从约 421kB 降至不高于 300kB；若构建工具计算口径变化，必须同时保留改造前后同环境对比，并至少降低 25%。
- 首次稳定渲染不超过 40 个笔记卡片节点。
- 初始无障碍树节点数相较基线至少降低 70%。
- 打开页面时，不因固定计时器自动下载富文本编辑器代码。
- 30 条与 1000 条账户在首屏渲染的卡片数量保持同一数量级。

### 6.2 P2-2：统一视觉系统，同时保留个性

#### 全站基础语言

- 以安静靛蓝、暖灰中性色和高可读正文色作为基础。
- 统一字体、字号层级、行高、圆角、边框、阴影、页面宽度、间距和焦点环。
- 主要内容通过排版、留白和分隔建立层级；卡片只用于确实需要边界的对象。
- 毛玻璃只允许用于覆盖在内容之上的短暂层级，例如导航或 Drawer；不能成为所有容器的默认样式。
- 避免通用 AI Dashboard 的渐变背景、彩色进度条、全大写英文标签和多层嵌套卡片成为主视觉。

#### 产品识别点

视觉个性来自“关系与记忆”：

- 两段来源之间的连接表达。
- 清晰的时间距离和来源状态。
- 可解释的关系类型，如延续、变化、张力和共同起点。
- 克制的线、节点或引用标记。

这些表达必须承载信息，不能退化为随机装饰线或无意义渐变。

### 6.3 P2-3：Profile 受控氛围色

#### 保留内容

- 用户资料编辑。
- 笔记统计。
- AI 兴趣、专长、传记、推荐和主题生成结果。
- 动态主题名称和主题理由。

#### 新视觉规则

- 动态氛围色只映射到 `--atmosphere-accent`、`--atmosphere-soft`、`--atmosphere-glow` 三类装饰 Token。
- 允许用于 Profile Hero 背景的低对比渐变、头像光晕、主题预览样本和少量关系标记。
- 禁止用于正文颜色、普通卡片背景、主按钮、错误/成功状态、焦点环和信息层级。
- 动态颜色进入页面前必须经过亮度、饱和度和对比度约束；解析失败时回退到默认靛蓝主题。
- 页面主体回到单一内容列或主次明确的响应式布局，减少空洞右栏和多层子卡片。
- “兴趣百分比”和“Expert”等模型推断不能借助鲜艳进度条伪装成精确测量；改用自然语言、来源数量和更新时间表达可信度。
- 中英文标签统一，不再混用“每日推荐 (For You)”一类无意义双语标题。

#### 验收

- 更换任意氛围色不会改变正文和操作的对比度。
- Profile 与 Memory 并排截图能够明显看出属于同一产品。
- 关闭背景图和渐变后，页面信息层级仍然成立。

### 6.4 P2-4：Auth 保留简洁质感并品牌化

#### 保留内容

- 单卡片、低干扰、明确表单的简洁结构。
- 登录、注册、重置三个模式。
- 精细间距、克制阴影和直接反馈。

#### 调整内容

- 移除代码和视觉中的“Apple Style”品牌依赖。
- 使用 NoteWithAI 的字体、靛蓝主色、共享按钮、输入框、焦点和错误 Token。
- 品牌图形不再使用通用记事本 Emoji；使用文字标识或可复用的关系/记忆符号。
- 登录页背景可以保留安静的层次，但不得成为与应用内部无关的灰色系统页面。
- light/dark 通过同一主题机制控制，不能只有 Auth 单独监听系统偏好。
- 三个模式使用 tabs 语义或等价的明确分段控制，并正确表达选中状态。

#### 验收

- Auth 与登录后的 TopNavigation、Button、Input、反馈信息使用同一组 Token。
- 去掉 Logo 文本后，仍可通过颜色、排版和控件辨认其属于 NoteWithAI。
- 认证业务请求、校验和跳转行为无回归。

### 6.5 P2-5：动效和 reduced-motion

#### 规范

- 动效只解释状态变化：创建、保存、关联出现、抽屉开关、确认和撤销。
- 常规反馈时长使用 150–250ms；复杂位移最多 350ms。
- 避免同时使用位移、缩放、模糊、旋转和弹簧造成过度表达。
- 所有非必要动画在 `prefers-reduced-motion: reduce` 下取消；必要状态变化改为无位移的即时或淡化反馈。
- 不使用 `transition: all`。
- 不在长列表滚动期间持续触发 layout spring、filter 或 backdrop blur 动画。

#### 验收

- 开启系统“减少动态效果”后，主流程没有大幅移动、弹跳或摇晃。
- 关闭动画不会隐藏状态变化或造成操作结果不明确。
- 样式扫描中不再出现没有属性范围的 `transition: all`。

## 7. 设计系统架构

### 7.1 Token 分层

Token 分为四层：

1. **Primitive**：中性色阶、靛蓝色阶、红/绿/黄状态色、字体尺寸、间距和圆角。
2. **Semantic**：`text-primary`、`text-secondary`、`surface-page`、`surface-raised`、`border-subtle`、`action-primary`、`focus-ring` 等。
3. **Component**：Button、Input、Navigation、Dialog、Card 等组件级 Token，只在确有组件差异时建立。
4. **Atmosphere**：Profile 专用装饰 Token，不得被基础组件依赖。

组件只消费 Semantic 或 Component Token。业务页面不得直接引用 Primitive 色值，也不得新增未经登记的十六进制颜色。

现有 `globals.scss`、`_variables.scss` 和 Tailwind HSL 变量收敛为同一来源，避免三套命名表达同一颜色。迁移期间提供兼容别名，所有页面迁移后删除别名。

### 7.2 排版

- 选择一套明确支持中文的 UI 字体栈，并使用项目实际加载的字体变量作为首选。
- 拉丁字符和数字可以使用同系列或兼容字体，但不形成另一套产品气质。
- 正文最小默认字号 16px；辅助文字原则上不低于 13px，并仍需满足对比度。
- 页面标题、区块标题、正文、元信息只保留必要层级。
- 每页只有一个 H1；品牌 Logo 不参与页面标题层级。

### 7.3 基础组件

本次治理优先复用并强化以下基础组件，而不是继续在 CSS Module 中复制规则：

- `Button`：primary、secondary、ghost、destructive、icon。
- `FormField` / `Input` / `Textarea`：label、description、error、required。
- `Dialog` / `Drawer`：完整焦点与背景隔离。
- `TopNavigation`：桌面与移动布局。
- `Menu`：键盘导航、关闭和焦点归还。
- `Surface`：少量有语义的页面层级，不形成“所有内容都是卡片”。
- `EmptyState`：标题、解释、下一步，不强制添加插画。
- `RelationshipCue`：跨 Notes、Memory、Profile、Chat 复用的关系表达。

基础组件不得绑定具体业务数据；页面组件负责把业务状态映射到 variant 和内容。

## 8. 页面迁移要求

### 8.1 Notes

- 优先修复移动卡片、关系入口和触控目标。
- 引入分页与渐进加载，解除关系抽屉对全量笔记的依赖。
- 卡片降低阴影和玻璃效果，正文与元信息建立明确层级。
- 创建、编辑、保存和 AI 富化状态继续遵守核心体验 Spec，不因视觉改造丢失草稿保护。

### 8.2 Chat

- 移动端历史抽屉使用共享 Drawer。
- 会话条目改为语义操作，删除动作始终可以通过键盘和触控发现。
- 输入区保留底部聚焦体验，发送按钮使用统一触控尺寸和焦点样式。
- 辅助声明、时间和空状态满足对比度。

### 8.3 Memory、Inspiration、Publish

- 修复 Memory 主按钮和内联 Dialog。
- 保留来源、隐私和用户控制文案。
- Publish 空状态的进一步内容优化属于 P3，不阻塞本 Spec，除非组件迁移自然覆盖。

### 8.4 Profile

### 8.5 Auth

- 执行第 6.4 节的品牌化简洁方案。
- 补齐表单 label、错误关联、密码按钮名称和模式选择语义。
- 不改变认证 API 和安全规则。

## 9. 响应式规范

统一使用内容驱动的断点，不允许每个页面自由定义互相冲突的移动规则。最低验证矩阵：

| 视口 | 主要用途 | 必须验证 |
|---|---|---|
| 320px | 最窄支持宽度 | 导航、长标题、表单、Drawer |
| 360px | 常见小屏 | 单手主操作、聊天输入 |
| 390px | 当前问题复现基线 | Notes、Profile、Memory |
| 768px | 平板/断点边界 | 导航切换、双栏收敛 |
| 1024px | 小型桌面 | 内容宽度、Drawer、Profile |
| 1440px | 标准桌面 | 留白、行长、层级 |

附加要求：

- 支持 200% 浏览器缩放。
- 支持长中文标题、长邮箱、无空格英文和大字号系统设置。
- fixed/sticky 元素不得遮挡焦点目标和最后一条内容。
- 表单出现错误时不能引发布局不可恢复的跳动。

## 14. 风险与控制

| 风险 | 控制方式 |
|---|---|
| Token 迁移造成大面积视觉回归 | 先建立兼容别名，按页面迁移，每阶段保存视觉基线 |
| Profile 动态色产生不可读组合 | 只输出受限装饰 Token，固定正文与操作 Token，失败时回退靛蓝 |
| Auth 统一后失去原有精致感 | 保留布局比例、克制阴影和微交互，通过排版与细节而非复制品牌表达质感 |
| 分页破坏关系抽屉 | 先让关系接口返回候选摘要，再切换笔记列表分页 |
| 虚拟化破坏搜索、焦点或读屏 | 分页优先；只有测量仍超预算时才虚拟化，并单独验证辅助技术 |
| 基础组件一次重写过多 | 先覆盖 P1 所需组件，再逐页迁移，不做无关组件重构 |
| 动画减少后状态反馈变弱 | 用文字、图标、位置和颜色共同表达状态，动效只作为增强 |

## 15. 后续工作方式

用户批准本 Spec 后，再创建逐任务实施计划。实施计划应把每个阶段拆成独立、可测试、可回滚的纵向切片；先完成阶段 A，不与 Profile 全面重构或笔记分页混在同一次改动中。

每个切片完成后记录：修改范围、自动化结果、人工验收视口、剩余风险。全部阶段完成后重新执行 Impeccable audit，并将新评分和未解决项回写到实施记录。
