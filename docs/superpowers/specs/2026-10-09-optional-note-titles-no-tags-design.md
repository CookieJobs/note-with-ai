## 1. 产品判断

### 1.1 结论与成立条件

建议采纳：新笔记默认无标题，用户可以手写标题或主动调用 AI 生成；标题始终可清空；退出用户标签及个人笔记话题系统。

这是一次有代价的产品取舍，不是由“界面更简洁”就能证明正确的改动。方案成立必须同时满足：

1. 无标题是完整的笔记形态，保存、阅读、引用、打开原文均可用。
2. 取消默认命名后，引用中仍有真实正文线索和日期帮助辨认来源。
3. 标签退出同时停止后台提取和消费，不把原系统换名后隐藏运行。
4. 既有正文、标题、手写标记及历史标签数据不被静默清空。
5. 关联、聊天和灵感所需的正文理解继续工作，处理范围不因此扩大。

如不能兑现这些条件，方案就是把现在的界面负担转移到将来的阅读和找回，应暂缓发布。

### 1.2 为什么标题可选合理

个人笔记混合了短句、随想、待办和长文，强制给每篇内容补上独立标题，会令短记录重复、长记录被模型提前定性。标题可选将命名权交给作者；按需生成保留了长文和命名困难时的帮助。

不能以“现有自动标题都没有价值”为理由：本轮看到的历史标题大体能概括内容，部分存在泛化。取消自动标题的核心依据是允许作者决定是否命名，而不是宣称自动概括普遍失败。

代价是真实的：默认无标题后，长笔记、相似开头及图片记录更难扫读；一键生成仍需要额外操作。这些代价通过显示契约和体验验收控制，不能承诺完全消失。

### 1.3 为什么此时可以退出标签

当前定位侧重个人记录、AI 对话、关联与灵感，尚未建立完整的用户分类工作流。卡片标签点击进入编辑，个人话题无法下钻到原笔记，因此目前的维护成本缺少直接回顾收益。继续建设意味着还要承担命名一致性、分类导航和长期治理；本期选择不沿这条路径继续投入。

251 篇笔记衍生 1,012 个话题、923 个仅涉及一篇的本地样本，说明当前提取粒度及呈现存在问题。它不是“低频标签无用”或“所有用户都不需要标签”的证据。

最强反方论据必须保留：用户在正文写过 `#复盘反思/AI英语`，说明其有主动组织意图。AI 关联与对话不能等价替代按自己主题回顾的可预测性。标签退役意味着放弃这条产品路径；正文中的手写标记仍原样存在，但本期不提供按标记筛选。

### 1.4 备选方案

| 方案 | 收益 | 成本与风险 | 本期结论 |
| --- | --- | --- | --- |
| 标题可选、按需生成、标签及个人话题退出 | 记录规则明确，减少可编辑派生信息和长期分类治理 | 无标题辨认成本增加，放弃结构化主题回顾 | 推荐，须满足本 spec 的边界 |
| 标题可选，仅取消 AI 提词，保留手工标签 | 保留用户组织路径 | 仍需要标签入口、筛选和治理，容易成为未完成的分类产品 | 暂不采纳，不能偷偷作为本期折中 |
| 继续自动标题和标签，改善生成与下钻 | 维持自动整理体验 | 需要解决一致性、质量和治理，不能只调 prompt | 是另一条合理路线，本期不实施 |

不承诺取消这两项会显著降低总体 AI 成本。摘要、概念扩展和关联仍有调用，收益主要是命名权、记录体验和明确的功能边界。

## 2. 用户意图、目标与非目标

### 2.1 已明确的用户要求

- 不再在保存笔记时自动生成标题和标签。
- 用户写标题则有标题，不写则无标题。
- 用户可以在写笔记时主动点击按钮，根据当前内容生成标题。
- 整个标签系统退出。
- 对方案进行独立、严格的产品判断，判断成立后撰写落地 spec。

### 2.2 本稿的推荐落地决策

- 标题生成结果直接填入当前编辑器的标题草稿，不自动写入已保存笔记。
- 历史标题保留；用户可逐篇清空。
- 个人中心笔记话题区域及其索引、回填、重试退役。
- 历史标签和话题数据暂存为退役数据，不进入正常产品读取及 AI 输入。
- 自动摘要、现有语义向量及用于关联的内部概念扩展继续服务既有能力。

这些是本稿提出的具体决策；用户审阅本文件后，才能作为实施依据。

### 2.3 非目标

- 不建设新搜索、标签树、文件夹、主题聚类、知识图谱或替代话题墙。
- 不改变聊天会话自动命名、灵感结果标题及来源网页标题。
- 不重做整个笔记页、聊天页、个人中心或视觉系统。
- 不重写画像算法；画像、账户、统计、头像仍按现有契约运行。
- 不批量重新生成摘要、向量、推荐或历史标题。
- 不清理数据库历史标签，不把标签移植到正文，不新增导出系统。
- 不增加图片识别作为标题生成能力。

## 3. 标题与显示名称的数据语义

### 3.1 真实标题

- 正常笔记 DTO 的 `title` 必须为字符串；无标题统一为 `""`。
- 新建请求省略 `title`、传空串或仅空白，均保存为 `""`。
- 手写标题经首尾 trim 后最多 100 个 Unicode code points；内部空白及原语言保留，标题为单行。
- 超长、多行或非字符串的写入明确返回校验错误，不能静默截断。
- 读取历史标题不因新长度约束改写或拒绝整篇记录；用户下次修改标题时应用新写入校验。
- 正文首行、H1、Markdown 标记均不自动转为独立标题。
- 清空标题是普通用户更新；正文后续编辑或后台维护均不会补回标题。
- 标题不作为笔记标识，定位、删除、引用和缓存仍使用 noteId。

### 3.2 纯展示的识别线索

正文卡片：有标题显示标题，无标题直接显示正文；保留独立日期与操作区域，不显示空标题行、命名占位或标题骨架。

关联和聊天等引用入口采用统一显示规则：

1. 真实标题 trim 后非空：显示真实标题。
2. 无标题：从服务端规范化正文取首个非空文本行，折叠连续空白，以最多 48 个 Unicode code points 的原文片段显示；超长加省略号。
3. 有图片而无可读文字：显示“图片笔记”并附创建日期；有多张图片可附图片数量。同日多篇图片记录需要时间及首图缩略图辅助辨认，复用现有图片展示与访问规则，不增加图像理解调用。不能仅凭空文本把无图片的历史异常记录归为图片笔记。
4. 已保存的历史引用仅有 noteId、没有可读正文：显示“笔记 · 日期”；若日期也未知显示“查看原笔记”。链接继续有效，不能伪造摘录。

正常引用应显示真实笔记 createdAt，使用上海时区；聊天消息或引用加入时间不能冒充笔记创建日期。旧快照日期无法核实时按未知处理。需要更多区分时可展示时间及第二行原文预览。摘要不能冒充原文摘录。

上述识别线索不回写 `title`、不更新 noteId、revision 或 updatedAt，也不作为标题参与模型命名。相似开头仍可能相似，这是标题可选的已知代价；不能借此偷偷恢复 AI 显示标题。

### 3.3 历史命名权

历史 `titleOrigin` 只有 `default/user`，不能可靠识别所有标题的真实作者。因此不按来源推断批量删除，不强制用户逐篇重新确认。

历史标题原样保留。标题写入管理不再由 `titleOrigin` 决定；自动后台链路无论来源是什么均没有标题写权限。新建及用户更新不再写入该退役来源字段，也取消其 schema 默认注入。

## 4. 新建、编辑与草稿

### 4.1 新建笔记

- 默认聚焦正文；保存条件仍为正文有效，独立标题不能单独构成笔记。
- 收起的快速记录入口只承担开始记录的任务，不展示标题输入或 AI 标题操作。
- 展开进入编辑后，正文上方自然出现“标题（可选）”空输入，默认仍聚焦正文。空标题失焦后保留输入区域，直到整份编辑器收起；无需额外点击“添加标题”。
- 正文有可用文字后，标题栏旁才出现“帮我拟个标题”次要按钮；空白、只有空格或纯图片时不显示，清空正文后再次隐藏。按钮有明确描边、底色和悬停/键盘焦点反馈，不使用纯文字样式。点击后用 AI 根据本次正文草稿拟标题，不需要先保存笔记。
- 有效结果填入标题输入并使其可见，用户可修改、清空或撤销最近一次生成填入。
- 保存同时提交当前标题及正文。标题为空时直接保存完整无标题笔记。
- 生成过程不阻塞正文编辑、保存、收起或取消。

### 4.2 已保存笔记

- 阅读态只显示真实已有标题和正文，不展示“添加标题”“编辑标题”“AI 生成标题”，无标题时不占空标题行。
- 点击已有标题进入整篇笔记编辑并聚焦标题；点击正文进入同一编辑器并聚焦正文。标题本身支持键盘操作，可访问名称包含实际标题。所有笔记在操作区统一提供“编辑笔记”按钮，不按有无标题区分；点击后进入同一编辑器并聚焦正文。取消后焦点返回本次编辑入口。无标题笔记在编辑中可自行添加标题。
- 编辑时正文上方始终显示“标题（可选）”输入，有可用正文文字时旁边提供“帮我拟个标题”描边按钮，以及生成后可用的“撤销生成”。新建与已有笔记复用同一标题栏，阅读态无 AI 状态或生成入口。
- 同一笔记编辑会话共享一份 title/body 草稿和一个 expectedRevision 基线。一次保存提交该会话所有 dirty 字段；仅改标题时不发送未修改正文。
- 标题输入、正文和标题 AI 操作构成同一编辑表单，标题栏与正文之间切换焦点不会关闭编辑或清空草稿。全篇只提供一组明确可见的“保存 / 取消”，不再提供独立“保存标题”按钮。
- 标题栏普通 Enter 转到正文；Cmd/Ctrl + Enter 保存整篇草稿，中文输入法选词时不触发提交；标题栏 Escape 与“取消”一致，放弃本次草稿。
- 清空标题并保存后，显示无标题卡片，日期、删除、关联、编辑操作保留。
- 普通失焦或收起保留草稿；“取消”明确放弃本次会话的标题和正文更改。
- 冲突返回保留本地草稿，显示服务端已变化的事实，用户显式重试；不得自动强写或自动合并两个标题。
- 保存成功后，expectedRevision 基线推进到该次成功响应的 revision，dirty 相对服务端接受的提交快照重新计算。保存期间的新编辑保留；仍有 dirty 时不收起编辑器，下次保存使用新基线，不与刚刚成功的自身写入冲突。

### 4.3 新建草稿持久化

- 当前按账号隔离的 localStorage 草稿扩展为 version 2：`title/text/json`。
- 兼容 version 1 和旧未版本化草稿，缺少 title 按 `""` 恢复；正文和富文本恢复规则继续保留。
- 任一标题或正文非空即视为草稿；只有标题的草稿也要保留，但不能保存为空正文笔记。
- 手写标题、清空标题、采用 AI 结果均递增草稿版本并持久化。
- 提交捕获 title/body 的同一快照。保存成功仅清除未被继续编辑的同一会话草稿；保存期间后来输入的标题或正文必须保留。
- 本机存储失败显示真实状态，不能承诺可刷新恢复。取消清理失败时保留草稿并报告失败，不能假装取消成功。
- 已保存笔记的草稿沿用现有保存位置，本期不另建全站草稿服务；刷新后的恢复能力不得被夸大。

## 5. 主动 AI 标题生成

### 5.1 生成与保存分离

生成请求只返回建议，不创建笔记、不写标题、不推进笔记 revision、不更新 updatedAt、不排队摘要、向量、话题或推荐。

有效建议只填入当前本地标题草稿；当前会话的“保存”才形成用户写入。已有标题的重新生成也仅在草稿中替换，可撤销或取消，没有额外确认弹窗。

### 5.2 请求状态与并发

生成状态使用 `idle/generating/failed`，与笔记保存状态分离。同一编辑会话至多一个在途请求；生成中按钮显示“生成中…”，其余记录操作可用。

每次点击捕获：`userId、editorSessionId、clientRequestId、bodyDraftVersion、titleDraftVersion`。响应仅在五项仍匹配、编辑器仍打开且结果属于最新请求时可填入。

下列事件使请求失效，并尽力 abort：正文编辑、标题编辑、保存开始、取消、收起、切换笔记、删除笔记、组件卸载、退出或切换账号。

必须以递增版本判断；正文或标题 A→B→A 后也不能应用原请求。Abort 失败不影响失效判断。迟到响应不能重开编辑器、填入另一篇笔记、改写已保存内容或清空后来草稿。

失效时立即退出该请求的本地 generating 状态。成功、catch 和 finally 的任何状态更新都须核验请求及会话身份；旧错误不能污染新会话，旧 finally 不能解除新请求的忙碌状态。

生成中点击保存：立即按点击时草稿保存，同时使生成请求失效；不等模型。重试重新截取当前正文，不重放旧失败正文。

### 5.3 接口契约

新增登录态接口 `POST /api/notes/title-suggestions`，注册在笔记动态 `/:id` 路由之前。

请求：

```json
{
  "body": { "kind": "plain-text", "text": "本次草稿正文" },
  "clientRequestId": "客户端生成的 UUID"
}
```

也接受现有 rich-text body 结构，由服务端复用正文规范化，不信任客户端另传的 contentText。不读取其他笔记，不接受跨账号 noteId 代取正文。

成功响应沿用统一 success envelope：

```json
{
  "success": true,
  "data": {
    "title": "建议标题",
    "clientRequestId": "原客户端 UUID",
    "sourceFingerprint": "规范化本次正文的 SHA-256"
  }
}
```

sourceFingerprint 不落入笔记；前端应用结果以编辑会话版本为准，不只比较文本哈希。

| 情况 | HTTP / code | 用户结果 |
| --- | --- | --- |
| 未登录 | 401 / 沿用认证错误 | 草稿仍在，不调用模型 |
| 无效 body、空正文或无效 requestId | 400 / NOTE_TITLE_INPUT_INVALID | 保留草稿，明确说明 |
| 只有图片而无可用于命名的文字 | 422 / NOTE_TITLE_TEXT_UNAVAILABLE | 可手写标题，不猜图片内容 |
| 正文超过输入限制 | 413 / NOTE_TITLE_INPUT_TOO_LONG | 提示内容过长，可手写；不静默截断 |
| 额度或在途限制 | 429 / NOTE_TITLE_RATE_LIMITED | 可继续记录，给 retryAfterSeconds |
| 未配置提供方 | 503 / NOTE_TITLE_PROVIDER_UNAVAILABLE | 可手写或稍后重试 |
| 提供方故障、结果校验失败 | 502 / NOTE_TITLE_GENERATION_FAILED | 不替换原草稿标题 |
| 整体超时 | 504 / NOTE_TITLE_GENERATION_TIMEOUT | 可重试，不阻塞保存 |

### 5.4 质量与调用预算

- 输入上限：规范化正文 12,000 个 Unicode code points，全量发送限制内正文；超限明确拒绝。本期不引入分块概括。
- 纯图片占位不作为语义内容；混合笔记只依据文字，按钮附近可说明“根据文字生成”。
- 独立标题 prompt：忠于原意，保留具体场景、实体和不确定语气；保持原文主要语言，保留产品或技术原名；不编造结论、不写营销标题、不按笔记中的指令改变系统任务。
- 建议长度以易辨认为目标，中文通常 8–24 字；硬校验为非空、单行、最多 60 个 Unicode code points。结果必须是严格对象中的字符串 title。
- 失败不能返回“未命名笔记”等假成功，不能截断无效输出后当作成功。
- 每个有效 API 请求最多一次提供方尝试；关闭此链路的默认 HTTP 自动重试。API 使用 30 秒整体期限，前端 32 秒整体期限，覆盖响应体读取；到期释放在途额度。
- 每账号最多 1 个在途请求、每分钟最多 5 次、每小时最多 30 次；标题服务进程最多 2 个提供方请求。在多实例下，账号限流和在途占用必须由共享持久存储原子执行，不能靠客户端禁用按钮或单进程 Map 保证。
- 共享在途占用使用过期租约及唯一 ownerToken。超时、异常或断连释放仅匹配自己的 token；进程崩溃后占用自动失效，迟到 finally 不能释放后来请求的占用。30 秒整体期限须 abort 底层 HTTP；进程并发槽持有至该传输结束，不能先释放槽位再让旧传输继续运行。
- 请求校验及鉴权通过后、调用提供方前占用额度；无效输入不消耗模型额度。提供方失败计入尝试额度；释放并发占用不返还已发生的尝试。
- 新增 `note_title` AI 用量操作；保留 note_meta/note_concepts，明确各自用途。日志、埋点不记录正文、标题文本或完整模型输出。

这些是首期设计预算，不是已经测得的性能或质量。真实质量验收必须使用代表性样例。

## 6. 标签及个人话题整体退役

### 6.1 产品与接口

- 删除卡片上的标签、添加、编辑、删除入口，以及旧备用笔记组件的标签展示。
- 删除个人中心笔记话题区域、范围筛选、覆盖数、刷新、重试、轮询及相关前端服务。
- 笔记正常 DTO 和请求类型移除 keywords；不增加同义的新公开字段。
- 新旧创建、更新适配器都拒绝显式 keywords 写入，返回 400 / NOTE_TAGS_RETIRED；包括空数组，不能悄悄接受或写库。
- 保留退役兼容响应：登录后的 `GET /api/profile/topics`、`POST /api/profile/topics/retry`、旧 `GET /api/recommend` 返回 410 / NOTE_TAGS_RETIRED。响应不查询笔记或话题集合、不启动任务。
- 继续保留 `/api/recommend/notes/:noteId`、`/api/recommend/semantic-notes`、画像 analysis 及账户/统计接口。
- 正文中的 `#`、斜杠、H1、手写标签和提及均原样保留，不自动解析为新分类、不删除、不补写为结构化字段。

### 6.2 后台处理

停止并撤除生产调用路径：

1. 新建、正文/标题更新后的话题调度。
2. 元数据完成后的话题调度。
3. 后端启动、数据库连接完成等两处 topic runtime 启动。
4. 定时用户扫描、旧笔记回填、索引 worker、租约、游标维护及手工话题重试。
5. 按 keywords 聚合的旧文章推荐消费。

生产构建中不存在可被入口激活的旧话题流水线；不保留自动正文话题回退。退役接口返回固定错误即可。

### 6.3 历史数据与删除语义

本期保留已存 keywords、keywordsOrigin、topicIndex* 及相关索引/回填/租约记录作为退役数据，不做批量物理删除。

- 正常读取、模型 prompt、推荐、画像和灵感均不得主动消费这些退役字段；不能用旧关键词补摘要或 concepts。
- 新记录不落退役字段；同时取消 Mongoose 的数组、来源和 topic fencing 默认值，不能留下自动注入的空字段。
- 一般保存、更新、启动及页面读取不改退役数据。用户删除笔记或账户时，保留已有按所有者清除其对应退役数据的逻辑；这是删除清理，不是话题整理。
- 不重排或修改历史创建/修改时间，不为退役做全库 revision 迁移。
- 后续物理删除单独形成迁移方案和授权；本期保留数据不等于承诺立即提供恢复界面。

## 7. 后台摘要及消费方适配

### 7.1 元数据任务职责

保留现有 `enrichment.meta` artifact 名称，职责缩减为正文 summary 和现有 concepts；embedding、recommendations 状态及 revision fencing 继续复用。

- 替换复合标题/关键词/摘要 prompt；生产后台不再计算标题或 keywords，不能算出来再丢弃。
- worker 的写入白名单只有摘要、概念及派生状态，不含 title、keywords 或对应来源字段。
- 空标题不能令 enrichment 永远 pending；笔记页取消标题/标签 skeleton，记录保存状态与后台语义整理状态分开。
- 正文文本变化按现有规则重新整理；纯格式改变沿用已有规则。已有标题在两种情况下均保持稳定。
- 单篇 summary 重生成、summary/ensure、管理员 meta 重试必须使用同一新链路；legacy 来源也不能被改名。
- 保留现有概念扩展仅用于内部语义召回，不能聚合为用户话题、显示成标签、开放编辑或驱动旧关键词推荐。
- 不借本期重写任务队列、并发系统或画像，也不批量回填新 prompt 的结果。

### 7.2 关联、聊天与来源链接

- 关联查询无标题时继续使用正文、摘要、概念及原有向量路径。
- 相关 DTO 的 title 返回真实空字符串，不能在后端填成“无标题”后冒充真实标题。
- 引用 DTO 补足显示需要的原文片段/类型及 createdAt，限制片段长度，不因为命名缺失扩大整篇正文返回；已有返回正文的契约不在本期重做。
- ChatMessage、ReferenceNote、聊天侧栏、关联抽屉、旧兼容引用及关怀来源均采用第 3.2 节的显示规则。
- 关怀来源链接的存在条件是有效 noteId，不能要求 noteTitle 同时存在。旧快照缺少片段时仍可打开来源。
- 新关怀来源携带真实笔记创建日期。旧 care_source 中由聊天加入时间填充的 createdAt 视为未知笔记日期，不直接展示为笔记日期。
- 标题清空后的引用和导航保留 noteId；同名或相似摘录不会改变目标。
- 本期受影响的关联、聊天和关怀引用，必须按有效 noteId 打开所属账号可访问的原文，不依赖笔记已在首页加载。必要时复用既有按 ID 读取接口及阅读容器；这是引用闭环的实施依赖和发布条件，不扩展为全库搜索。删除或无权限的来源显示明确不可用状态，不能跳到另一篇或静默失败。

### 7.3 灵感输入与既有处理范围

新的 LimitedNoteContext 为 noteId/revision/可选 title/summary，移除 keywords；planner、synthesizer 的 payload 与说明一起更新。

- 沿用按 updatedAt 最近 5 篇的选取；每篇标题最多 80 字符、摘要最多 120 字符，继续现有清理规则。
- 无标题且无标签，只要有可用摘要就必须能参与选题。摘要有 revision 标记时，须与当前正文版本对应；未知来源的历史摘要沿用兼容读取，不能伪称本次已核实。
- 不为替代 keywords 自动将原始正文片段发给灵感 planner/synthesizer；搜索提供方仍只收到规划出的搜索查询。
- 标题或摘要至少一项可用才进入规划；正常新笔记依赖既有摘要任务准备上下文，不因标题为空永久排除。
- 逐篇剔除不可用上下文；最近 5 篇中只要有一篇可用，就用可用条目继续规划，不能被另一篇 pending 阻塞。已知过期摘要不得参与，未知来源历史摘要按上述兼容规则处理。
- 所有选取笔记均无可用上下文时，不调用 planner、搜索或 synthesizer。手动请求返回 409 / INSPIRATION_NOTE_CONTEXT_UNAVAILABLE，details.reason 区分 no_notes、summary_pending、context_unavailable；分别提示先记录笔记、摘要准备中可稍后再试、当前笔记缺少可用标题或摘要。只有确实存在进行中的摘要任务才显示“准备中”；失败或纯图不能被永久解释为等待中。保留已有灵感。
- 定时任务沿现有 no_result 完成，记录 note_context_unavailable 及具体 reason，等正常下次调度，不另增快速重试。前端该类状态不显示“没有发现新来源”，因为本次并未执行检索。
- 不在 GET、打开页面或标题生成接口中暗中补摘要或启动研究。
- 灵感“保存”继续表示收藏灵感条目，不新增保存为笔记；灵感 headline、topicLabel 和网页来源标题仍按研究结果原契约工作，topicLabel 不承担笔记分类。
- 页面说明改为使用“笔记标题（若有）和短摘要”等真实字段。

### 7.4 画像和名称相同的非标签代码

画像继续根据原有受限笔记内容运行；只做空标题兼容。背景主题规则中的 keywords 匹配变量、聊天标题、网页标题等不是笔记标签，不能用全局字符串替换误删。

## 8. 兼容与切换

1. 不要求数据迁移即可读取历史笔记；title 缺失或 null 在 DTO 规范化为空串。
2. canonical 与 legacy 新建均支持可选 title；旧客户端省略标题时新建无标题。
3. PATCH 以及旧 POST 标题接口都支持清空标题并执行相同长度和单行校验。
4. 旧客户端发送 keywords 会得到明确退役错误；因此前后端作为同一发布单元切换，要求旧页面刷新，不静默吞掉更改。
5. 发布停止旧后端实例及 topic runtime，并清除旧任务在内存中的执行。不能混跑仍有标题/标签写权限的旧实例；旧任务写回防护需在实现计划中验证。
6. 标题生成接口与 title-only 写入不改变正文的向量；标题变化沿现有规则使推荐失效。body/title 同次更新只推进一次 revision。
7. 历史推荐/聊天快照按 noteId 继续工作，显示名称仅在渲染或重新读取时派生。
8. 历史保留数据支持后续回滚评估，但不能直接恢复有自动标题/标签写权限的旧后端。回滚版本必须先带上禁用这些写入的兼容修正，并兼容空标题和新建请求；不能把“可回滚”解释为可以违背用户已清空的标题。无法提供兼容回滚版本时，不宣称具备直接回滚能力。

### 8.1 线上存量兼容复核（2026-10-11）

当前实现不能直接删掉界面后发布。复核确认：新建仍取正文首行作标题；后台 meta、摘要修复和管理员重试能补回原标题/标签；标题和正文分别保存会产生自冲突；关怀的来源链接要求非空标题；列表外引用只尝试滚动；灵感仍消费关键词，并可能使用已知过期摘要。这些均作为本期修复项。

- 历史标题缺失、null、空串都可读；超出新写入限制的历史标题仍完整读取。未提交 title 的更新不能清空或重新校验旧 title，也不能截断旧值。
- 创建、PATCH、legacy POST 均检查原始请求中显式 keywords；不能靠 schema 丢弃未知字段掩盖退役写入。旧页面收到 NOTE_TAGS_RETIRED 时提示刷新，不能报保存成功。
- 单次标题和正文保存只递增一次 revision。标题单独修改不触发正文摘要/向量重算；已有可用派生状态推进到新 revision，推荐按原规则失效。
- 关怀与聊天历史快照缺少新显示字段仍可读取；不拿消息创建时间冒充笔记创建时间，不要求存在标题才能链接。
- 发布需要前后端一起切换并停掉旧后端进程；仅部署新前端无法阻止旧 worker 写回。发布前确认旧 topic 定时器和旧 meta 请求已结束，新 worker 写入白名单不存在 title/keywords。
- 不向线上数据运行清理或回填。本地兼容性与并发验证使用独立测试库，真实测试账号样本只读；本次实施授权不包含线上部署。

执行并记录：

1. 无标题写入一次短记录，检查是否增加额外步骤。
2. 仅凭列表/引用的内容线索辨认指定记录，再打开并核对原文。任务必须包含同日且相似开头的无标题笔记、同日图片笔记；记录耗时、误选和失败原因。
3. 给一篇长笔记主动生成标题，检查是否保留其具体观点和限定语；修改或清空后继续保存。
4. 通过现有聊天/关联/关怀引用回看旧内容，分别验证已加载和列表外笔记可打开正确原文；删除或无权限来源的明确不可用提示另测。
5. 无标题、无标签但有摘要的笔记参与灵感，核对输入及最终相关性；上下文未就绪时检查解释。

标题忠实度、辨识成本和打开正确原文是主要判断；页面变短、标签数量归零、点击次数下降不能单独宣告产品成功。无需新增全站埋点系统作为前置；人工任务记录和既有 AI 用量足以支撑首轮验收。

代表性辨认任务中，无法区分目标、误选目标或无法打开可访问原文，均使该项验收不通过。先用时间、第二行原文或首图预览等既定显示能力修正，再复测；不能以“已知代价”自动豁免。若仍希望接受失败，必须明确列出具体场景并另作产品决策，本稿不预先授权该例外。主动生成样例出现编造核心事实、反转观点或删除关键限定语，也须修正后复测。
