# 核心体验闭环设计 Spec：捕捉、关联与回望

- 状态：分轮实施；本轮为桌面 Web 快速记录的草稿保护与保存反馈，关联等后续章节尚未完成
- 日期：2026-09-01
- 本轮更新：2026-09-09，用户确认优先桌面 Web，移动端优化延后
- 对应审计：`.impeccable/critique/2026-08-29T17-18-59Z__frontend-src.md`
- 执行方式：每轮选择一个问题，完成实现与验收后回写本 Spec，不另建重复的完整 Spec

## 1. 决策摘要

本 Spec 将产品从“带 AI 功能的笔记工具”收敛为一个清晰闭环：

> 捕捉当下 → 后台安静理解 → 发现笔记之间的联系 → 回到原文验证 → 继续记录或与 AI 对话

第一阶段不追求功能数量，而追求两个可被用户直接感知的结果：

1. 用户在桌面 Web 会后或念头刚出现时，可以立即开始写；刷新、切换页面和收起记录器后可以恢复未提交的草稿。
2. 产品能用普通人的语言解释两条笔记为什么有关，而且允许用户纠正错误关联。

数值相似度、算法类型和内部评分继续保留给诊断与调试，但不再构成普通用户界面。

## 2. 背景与问题

目标用户是已经有记录习惯、但经常错过转瞬即逝想法的人。当前实现具备笔记、富文本、AI 富化、相关推荐与聊天能力，但核心价值被三个问题削弱：

- 记录入口更像“发送消息”或打开编辑器，移动场景下步骤和视觉负担偏重。
- 笔记关系藏在侧边入口中，并以 `s1`、`s2`、综合分和技术标签表达；用户看见了算法，没有看懂自己。
- 新用户在笔记较少时缺少预期管理，不知道需要记录到什么程度、之后会获得什么。

本 Spec 解决主闭环，不承担全站视觉重构，也不扩展社交网络、公开分享或主动内容推荐；这些由第二份 Spec 或后续整合处理。

## 3. 目标与成功标准

### 3.1 产品目标

- 把首页首要动作明确为“记下这一刻”。
- 当前优先桌面 Web 的记录可靠性与反馈；移动端单手记录和结构性重排延后。
- 把推荐结果改造为带证据、可理解、可纠正的“关系线索”。
- 为冷启动阶段提供安静、非任务化的进度反馈。
- 让一条有价值的关系自然导向“继续写”或“和 AI 聊聊”。

### 3.2 核心成功事件

用户完成一次“价值闭环”的定义为：

1. 创建一条笔记；
2. 系统后来为它展示至少一条关系线索；
3. 用户打开相关原文；
4. 用户随后执行“继续写”或“和 AI 聊聊”中的任一动作。

该事件比单纯记录数、停留时长或聊天轮数更接近产品价值。

### 3.3 建议观测指标

- 首次进入到首条笔记保存成功的中位时长。
- 快速记录打开后保存成功率、草稿恢复率、保存失败率。
- 有资格生成关系的笔记中，获得至少一条可展示关系的比例。
- 关系线索打开率、回看原文率、`helpful` / `not_relevant` 比例。
- 完成上述价值闭环的用户比例及所需天数。

这些是事件契约，不要求本 Spec 引入第三方分析平台。若项目尚无统一埋点设施，应先写入结构化服务端日志；后续再接分析系统。

## 4. 非目标

- 语音录制、音频上传与语音转写。它对步行/跑步场景很重要，但需要独立确定供应商、隐私提示、失败降级和成本模型；本阶段只保证输入架构未来可增加 `captureMode: voice`。
- 全站设计系统重构、品牌换肤和所有历史页面的样式统一。
- 社交关注、动态流、点赞、评论和用户主页。
- 公开分享、AI 记忆治理、网络内容推荐；见第二份 Spec。
- 将任意 AI 推断直接写成用户的固定人格结论。
- 用连续签到、积分或强制新手任务推动记录。

## 5. 体验原则与不可破坏约束

1. **记录优先于整理。** 打开入口即可输入，不要求先选分类、标签或模板。
2. **本地先保住内容。** 网络失败不得清空输入，关闭浮层不得等于丢弃草稿。
3. **关系必须可验证。** 每条关系都要展示来自两篇原文的证据片段，并可打开原文。
4. **解释优先于评分。** 用户界面不展示 `s1`、`s2`、综合分或小数置信度。
5. **AI 使用试探性语言。** 使用“可能”“这两条都提到”“这里似乎有变化”，避免人格定论。
6. **用户拥有纠错权。** 每条关系都可标记有帮助、不相关，或永久隐藏这一对。
7. **不制造打扰。** AI 富化在后台进行；处理中有轻量状态，不阻止继续记录。
8. **私密默认。** 本闭环中的所有内容和关系只对当前用户可见。

## 6. 目标用户旅程

### 6.1 第一次使用

首页空状态只解释一件事：

> 先记下一件刚刚发生的事。记录多起来后，这里会帮你找到过去与现在的联系。

主按钮为“记下这一刻”。下方可给出三条可直接点选、但不强迫回答的提示：

- 刚刚有什么让你停顿了一下？
- 今天哪次对话还留在脑子里？
- 现在最不想忘记的念头是什么？

点选只把提示放入输入框的辅助区域，不作为笔记正文，也不自动发送。

### 6.2 日常快速记录

1. 用户点击固定但不遮挡内容的“记下这一刻”。
2. 输入面板立即聚焦正文；默认只出现正文和保存按钮。
3. 标题、格式、标签等能力通过“更多”展开。
4. 输入内容实时保存在本地草稿中。
5. 用户保存后立即看到笔记；AI 富化显示为非阻塞的“正在理解这条记录”。
6. 保存成功后清除对应草稿；请求失败则保留草稿并允许重试。

### 6.3 第一次出现关系

当系统第一次找到有意义的关系时，在新笔记卡片附近展示一张克制的关系卡：

> 这条记录可能和你 3 月写下的一个念头有关

卡片同时提供：关系类型的人类语言、两段原文证据、日期，以及“看看原文”。关系不是弹窗，不抢占输入焦点。

### 6.4 回望与延续

打开关系后，用户可：

- 查看两篇完整原文；
- 标记“有帮助”或“不太相关”；
- 选择“以后别再关联这两条”；
- 选择“继续写”，创建一条带内部来源上下文的新草稿；
- 选择“和 AI 聊聊”，进入聊天并带入这两篇笔记，但不自动向 AI 发送消息。

## 7. 功能设计

### 7.1 快速记录入口

现有 `FloatingQuickCompose` 继续作为入口，但重新定义为捕捉器而不是缩小版完整编辑器。

#### 默认状态

- 文案：`记下这一刻`，不用“发送消息”。
- 默认只展示正文输入、关闭和保存。
- 本轮保留桌面端宽度受控的记录器；移动端底部面板留待后续迭代。
- 正文为空时保存不可用；仅空白、不可见字符或空富文本不得提交。
- 所有主要触控目标最小 `44 × 44 CSS px`。
- 支持键盘提交，但快捷键必须在界面中可发现；`Esc` 关闭前不得清空草稿。

#### 渐进披露

“更多格式”展开现有富文本工具；标题为可选字段。展开状态可以记住，但不能让首次使用默认变复杂。

#### 草稿规则

- 使用按用户隔离的本地键，例如 `quick-capture-draft:<userId>`。
- 本轮保存新建笔记的正文文本、富文本 JSON、存储格式版本和更新时间；不新增标题或编辑模式控件，不扩展到已有笔记的编辑草稿。
- 正文变更时同步写入 localStorage，避免节流窗口内刷新或离页漏存最后输入；刷新页面、离开再返回或意外关闭后可恢复。后续若正文规模导致输入延迟，再考虑 IndexedDB 与必要的离页刷写。
- 保存成功才删除草稿。
- “收起”、点击记录器外部和 Esc 仅关闭编辑界面；有内容时入口显示“继续编辑草稿”。
- 用户主动选择“放弃草稿”时才清除；若内容非空，提供一次明确确认。
- 本地存储不可用时继续允许编辑，并以非阻塞提示说明无法自动恢复。
- 兼容没有版本号的旧 text/json 草稿；恢复时不改写原记录。富文本按现有编辑器 schema 校验，损坏时恢复文字并提示格式无法恢复。账号切换时重建记录器，避免保留旧账号的编辑器实例。
- 草稿属于当前账号和当前浏览器的本机存储，不承诺跨设备同步或浏览器清理数据后的恢复。

#### 保存与冲突

继续复用 `useNotes` 的创建和规范快照策略。乐观插入可以保留，但界面必须区分：

- `saving`：正在保存；
- `saved`：服务端已确认；
- `failed`：内容仍在草稿中，可重试；
- `enriching`：笔记已保存，AI 正在后台处理。

`enriching` 不是保存状态，不得阻止关闭捕捉器或创建下一条笔记。

本轮保存反馈规则：

- 提交后保持记录器打开，直到服务端确认成功才自动收起；用户仍可主动收起。
- 保存请求期间不允许再次提交或放弃，但可以继续输入；如果内容已变化，旧请求完成只确认旧版本，保留新内容并保持编辑状态。
- 保存失败保留正文和格式，在记录器旁显示失败状态，并提供“重试保存”。
- 保存成功后，独立显示“已保存到云端”和 AI 后台处理状态；AI 未完成不阻止下一次记录。
- 异步回调按用户会话和草稿版本校验；旧账号请求不得清空新账号输入，旧标签页请求不得删除另一个标签页更新的持久草稿。
- 同一账号的本机恢复槽位保存最近一次写入；本轮不提供多标签页实时合并、离线自动发送或服务端请求幂等协议。

#### 本轮验收范围

- 自动化覆盖：正文/格式恢复、旧格式兼容、损坏格式文字回退、账号隔离、失败后返回重试、成功清理、新输入与旧保存请求竞争、重复点击、存储不可用，以及页面组件的收起/确认放弃/保存反馈。
- 2026-09-09 验证结果：前端 27 个测试文件、165 项测试全部通过；TypeScript 类型检查通过。独立代码复查通过。
- 桌面 Chrome 已确认登录页面可达，并定位了旧草稿无版本号导致的恢复失败；兼容修复已由回归测试验证。最终浏览器复验遇到 ERR_BLOCKED_BY_CLIENT，正常重载仍被拦截，因此输入、收起、刷新恢复、明确放弃与焦点操作的完整手工验收仍待补齐，不将自动化结果当作浏览器验收通过。
- 本轮仅完成 7.1 中草稿与保存相关行为；关系领域模型、冷启动、关联反馈和后续闭环仍列为待实施，不将整份 Spec 标为完成。

### 7.2 冷启动与“关系正在形成”

不设硬性的“写满 5 条才能使用”门槛。关系算法有足够候选时即可工作；界面根据状态展示不同预期：

- 0 条：解释产品承诺，邀请记录第一条。
- 1 条：`已经记住这一刻。再有新的记录时，我们会开始寻找联系。`
- 多条但暂无关系：`还没有足够明确的联系。你可以继续自然地记录，不需要刻意分类。`
- 有关系：默认展示最近且未被用户处理的一条。

上述文案不是计数挑战，不显示进度条或“还差 N 条”。

### 7.3 关系的领域模型

现有推荐缓存可以继续保存算法诊断字段，但面向前端的新契约必须是人类可读的领域对象。

```ts
type RelationshipKind =
  | 'continuation'
  | 'contrast'
  | 'change'
  | 'tension'
  | 'shared_origin';

type ConfidenceBand = 'possible' | 'supported';

interface NoteEvidence {
  noteId: string;
  revision: number;
  excerpt: string;
  occurredAt: string;
}

interface NoteRelationship {
  relationshipId: string;
  source: NoteEvidence;
  candidate: NoteEvidence;
  kind: RelationshipKind;
  headline: string;
  explanation: string;
  confidence: ConfidenceBand;
  generatedAt: string;
}
```

约束：

- `headline` 是一句可独立阅读的发现，不超过 40 个中文字符为目标。
- `explanation` 必须同时依据两条笔记；不能只复述候选笔记。
- 两个 `excerpt` 必须来自对应 revision 的原文，不得由模型虚构。
- `confidence` 只用于控制措辞和排序，不显示数值。
- `relationshipId` 必须稳定，供反馈和隐藏使用。
- 如果任一笔记 revision 已变化，服务端需要重新验证或重新生成证据，不能继续展示失效摘录。

### 7.4 关系生成与排序

`recommendService` 继续负责候选召回，但增加一个面向体验的解释层：

1. 召回候选并计算内部 `s1` / `s2`。
2. 应用所有权、删除状态和用户隐藏关系过滤。
3. 选出少量候选后生成结构化关系解释。
4. 校验两个证据片段确实存在于对应笔记规范文本中。
5. 无法验证的结果丢弃，不向前端降级为虚构解释。
6. 同一来源笔记默认最多返回 3 条，优先展示证据明确且尚未处理的关系。

内部评分可记录到日志和缓存，不进入普通响应。开发调试需要查看时，使用仅开发环境开启的诊断字段或服务端日志。

### 7.5 关系展示

现有 `RelatedNotesDrawer` 改造成“关系线索”面板；入口不能只依赖难以发现的侧边把手。

最低展示要求：

- 在笔记卡片内或紧邻卡片处展示首条未处理关系摘要。
- 明确日期和两段证据的来源归属。
- 关系类型使用自然语言，例如“延续了之前的想法”“和过去的判断相反”“同一个困扰出现了变化”。
- 主动作是“看看原文”，次动作是“继续写”“和 AI 聊聊”。
- “为什么会看到这个？”解释两段证据如何支持关系，不解释向量、权重和算法公式。
- 用户反馈应在当前卡片内完成，不打开新的模态框。

### 7.6 关系反馈

在现有 `/api/recommend` 路由域内增加反馈接口，避免创建新的顶层路由：

```http
POST /api/recommend/relationships/:relationshipId/feedback
```

```json
{
  "sourceNoteId": "...",
  "candidateNoteId": "...",
  "sourceRevision": 3,
  "candidateRevision": 1,
  "verdict": "helpful | not_relevant | hide_pair"
}
```

新增独立 `RelationshipFeedback` 模型，至少保存：`userId`、两笔记 ID、两 revision、`relationshipId`、`verdict`、时间戳。数据库层对 `(userId, relationshipId)` 做幂等约束。

- `helpful`：保留关系，记录反馈。
- `not_relevant`：当前关系从默认未处理列表移除，但允许历史中查看。
- `hide_pair`：对该用户永久过滤这一对笔记的关系；笔记顺序必须规范化，避免 A-B 与 B-A 不一致。
- 反馈接口必须验证两条笔记都属于当前用户。

第一阶段反馈只用于过滤和质量评估，不直接在线更新模型权重。

### 7.7 “继续写”

点击后打开快速记录器，并把来源上下文保存在草稿元数据中：

```ts
interface CaptureContext {
  origin: 'relationship';
  relationshipId: string;
  sourceNoteIds: [string, string];
}
```

来源上下文不自动写入正文。界面显示一条可移除的说明：`正在延续两条过去的记录`。保存后可在服务端元数据或事件日志中保留来源，用于衡量闭环；不要给普通用户暴露内部 ID。

若当前 Note 模型没有安全的元数据扩展位，本阶段只发送产品事件，不为此修改 Note 核心 schema。

### 7.8 “和 AI 聊聊”

通过 URL 参数或 session state 把两条笔记带入聊天页：

```text
/chat?source=relationship&relationshipId=<id>
```

聊天页加载后向后端解析 `relationshipId`，再次校验所有权，再把两条原文作为可见的上下文卡片展示。输入框可以给出建议问题，但不得自动发送：

> 这两个时刻里，我的想法发生了什么变化？

用户可以移除任一上下文笔记。AI 回答必须能够标注它引用的是哪条笔记；关系解释本身不能替代原文。

## 8. 接口与数据流

### 8.1 推荐读取

保留现有推荐入口的兼容性，但为前端返回新的 `relationships` 结构。迁移期间可以同时在服务端保留内部候选缓存，前端新代码不得依赖 `s1`、`s2`。

建议响应：

```json
{
  "sourceNoteId": "note-1",
  "sourceRevision": 3,
  "status": "ready",
  "relationships": [],
  "generatedAt": "2026-09-01T00:00:00.000Z"
}
```

`status` 取值：`insufficient_history | enriching | ready | failed`。失败响应带可重试的稳定错误码，不把模型原始错误回传给前端。

### 8.2 一致性

- 关系缓存必须绑定来源和候选 revision。
- 笔记更新后，由现有 `NoteUpdateOrchestrator` 使旧关系失效，并进入重新富化。
- 笔记删除后，包含它的关系和未处理反馈不再对用户返回。
- 前端继续以服务端规范快照为准，不自行拼接一个“看起来成功”的长期状态。

### 8.3 产品事件

服务端结构化记录以下事件，字段不得包含完整笔记正文：

- `capture_opened`
- `capture_saved`
- `capture_save_failed`
- `capture_draft_restored`
- `relationship_shown`
- `relationship_opened`
- `relationship_feedback_submitted`
- `relationship_continue_writing`
- `relationship_chat_started`
- `value_loop_completed`

事件可包含用户匿名 ID、笔记 ID、relationship ID、耗时、客户端类型和错误码。不得写入证据全文。

## 9. 状态、错误与降级

| 场景 | 用户看到什么 | 系统行为 |
|---|---|---|
| 离线或请求失败 | “还没保存到云端，内容仍在这台设备上” | 保留草稿，允许重试 |
| AI 富化较慢 | “正在理解这条记录” | 不阻塞记录与浏览 |
| 候选不足 | “继续自然记录，联系会慢慢出现” | 不返回空白抽屉 |
| 解释生成失败 | 不展示该关系 | 记录错误并可重试，不展示内部候选分数 |
| 证据校验失败 | 不展示该关系 | 丢弃结果并重新生成 |
| 关系 revision 过期 | “这条笔记已更新，正在重新寻找联系” | 使缓存失效 |
| 反馈重复提交 | 保持已选状态 | 幂等更新 |
| 聊天上下文无权访问 | 明确说明上下文不可用 | 不把任何笔记内容交给模型 |

## 10. 无障碍与响应式要求

- 以 WCAG 2.2 AA 为目标。
- 所有图标按钮必须有可访问名称；不能只用 tooltip 表达名称。
- 键盘焦点顺序与视觉顺序一致，打开捕捉器后焦点进入正文，关闭后回到触发按钮。
- 反馈选择用真实 button/radio 语义并暴露选中状态。
- 颜色不作为保存、关系类型或反馈状态的唯一线索。
- 遵循 `prefers-reduced-motion`；富化和关系出现动画可被关闭。
- 移动端软键盘出现时，正文和保存按钮仍可见；不产生横向滚动。
- 证据摘录使用可选取文本，不能仅渲染为 canvas 或图片。

## 11. 安全与隐私

- 所有推荐、关系和反馈接口都必须由服务端从登录身份确定 `userId`，不信任请求体里的用户 ID。
- 关系解释传给模型的上下文限制为必要的两条笔记，并沿用项目现有模型调用和日志脱敏策略。
- 服务端日志不得记录完整正文、完整 prompt 或证据全文。
- 不把关系反馈用于跨用户推荐。
- “隐藏这一对”必须是账户级持久状态，而不是仅前端隐藏。

## 13. 测试策略

### 13.1 前端单元与组件测试

- 空正文不可保存，合法正文可保存。
- 草稿写入、刷新恢复、成功后清除、失败后保留。
- 关闭有内容的捕捉器不会静默丢失。
- 移动与桌面两种布局下主动作可访问。
- 用户界面不出现 `s1`、`s2`、`综合分` 或小数置信度。
- 每条关系展示两段来源明确的证据。
- 三种反馈正确更新状态；重复提交不制造重复记录。
- “继续写”带入上下文但不污染正文。
- “和 AI 聊聊”展示上下文但不自动发送。

### 13.2 后端单元与集成测试

- 候选召回、反馈过滤和隐藏 pair 的规范化。
- 关系解释结构校验与证据 substring 校验。
- revision 变化后缓存失效。
- 删除笔记后不再返回相关关系。
- 跨用户关系 ID、笔记 ID 和反馈请求全部拒绝。
- 反馈接口幂等。
- AI 服务失败、超时和非法结构均安全降级。
- 结构化日志不含正文。

### 13.3 回归测试

- 原有笔记创建、编辑、删除、冲突处理与规范快照测试继续通过。
- 原有聊天在没有 relationship 参数时行为不变。
- 旧推荐缓存存在时不会导致页面崩溃；可重新富化或安全忽略。

### 13.4 手工验收设备

- iPhone Safari 等效窄屏尺寸。
- Android Chrome 等效窄屏尺寸。
- 桌面 Chrome/Safari。
- 键盘-only 与 VoiceOver 基础流程。
- 慢网、断网、请求超时和页面刷新。

## 14. 验收标准

全部满足才视为本 Spec 完成：

1. 新用户无需选择分类即可在首页完成首条记录。
2. 有内容的快速记录在刷新、关闭和保存失败后均可恢复。
3. 记录保存和 AI 富化被明确区分，富化失败不影响笔记存在。
4. 关系入口在笔记主流程中可发现，不只存在于侧边把手。
5. 普通用户界面完全移除内部相似度分数和算法缩写。
6. 每条展示的关系包含两段可验证的原文证据及两篇原文入口。
7. 用户可以提交有帮助、不相关、永久隐藏 pair 三种反馈。
8. 隐藏 pair 在刷新和重新富化后仍不出现。
9. “继续写”与“和 AI 聊聊”均可从关系卡到达，且不自动发布或发送任何内容。
10. 所有权、revision、删除和 AI 失败路径有自动化测试。
11. 前后端现有测试、类型检查与新增测试全部通过。
12. 在窄屏和键盘-only 验收中没有阻断性问题，主要触控目标达到 44px。
