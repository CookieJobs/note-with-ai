# Related Notes Benchmark Seed

这是一组用于线上“相关笔记”能力验证的标准测试集。

- 不手工指定标题
- 只录入正文
- 标题由系统自动生成
- 目标是验证 `s1`、`s2`、阈值和误召回情况

## 使用说明

- 建议把下面每条正文作为一篇独立笔记创建
- 创建完成后，等待系统自动生成标题、embedding 和相关推荐缓存
- 验证时重点看“应该强相关”的笔记是否互相命中，以及“干扰项”是否被错误排到前面

## 预期关系

### A 组：产品部署与上线复盘

- `A1` 应强相关 `A2`
- `A1` 应中强相关 `A3`
- `A2` 应强相关 `A3`
- `D3` 可以和 `A` 组产生弱到中等相关，但不应压过 `A` 组内部的相关性

### B 组：AI Agent 产品设计

- `B1` 应强相关 `B2`
- `B1` 应强相关 `B3`
- `B2` 应强相关 `B3`

### C 组：个人知识管理与语义检索

- `C1` 应强相关 `C2`
- `C1` 应中强相关 `C3`
- `C2` 应中强相关 `C3`

### D 组：干扰项

- `D1` 不应和 `A/B/C` 组形成强相关
- `D2` 不应和 `A/B/C` 组形成强相关
- `D3` 是“工程上线流程”干扰项，允许与 `A` 组有一定相似度，但不应成为最强命中

## 正文清单

### A1

今天把产品第一次部署到服务器环境。整个过程里最耗时的是环境变量整理、容器启动、域名与端口映射。真正上线后，我发现比开发环境多出很多细节问题，比如日志排查、服务重启策略、健康检查和静态资源路径。

这次上线让我意识到，部署并不是“代码能跑起来”这么简单，而是一个完整的运维与验证流程。只要少一个检查点，线上问题就会被放大。

### A2

第二次部署产品时，我把流程重新梳理了一遍。我把环境变量、镜像构建、容器重启、数据库备份和回滚步骤都提前写成了 checklist。

这样做的好处是，部署从“凭经验操作”变成了“按步骤执行”，明显降低了线上风险。我越来越觉得，稳定上线能力本身也是产品能力的一部分。

### A3

真正让我紧张的不是上线本身，而是上线失败后能不能快速回退。如果没有备份、没有回滚路径、没有明确责任人，那么再小的改动都可能放大成事故。

所以上线前应该明确谁负责发布、谁负责验证、谁负责回滚。对产品团队来说，流程稳定性和功能本身一样重要。

### B1

很多产品在做 Agent 时，只是给用户一个聊天框，然后期待用户通过对话完成复杂任务。但真正好用的 Agent 产品，应该有清晰的任务结构、状态反馈和可中断流程。

如果用户不知道 Agent 正在做什么，也无法接管关键步骤，那么体验就会非常不稳定。我认为 Agent 的核心不是“能聊”，而是“能可靠地完成任务”。

### B2

Agent 在执行任务时，最怕的是黑箱。用户想知道系统现在是在理解需求、调用工具、等待结果，还是已经失败。

如果这些状态没有被清楚地展示出来，用户就很难信任这个系统。所以 Agent 产品设计必须把执行过程、阶段状态和失败原因可视化。

### B3

很多人以为 Agent 的目标是全自动完成任务，但我更认同“关键节点可接管”。用户并不是完全不想参与，而是不想处理低价值重复劳动。

当 Agent 在关键步骤允许用户确认、修正或接管时，系统反而更可信。因此，Agent 设计的重点不是完全替代人，而是让人机协作更顺畅。

### C1

很多人记笔记只是为了留档，但真正有价值的笔记系统应该支持未来再次调用。如果一条笔记记完以后再也不会被检索、关联、复用，那它就只是被动存储。

我越来越觉得，笔记产品的核心价值在于让过去的内容重新参与当前思考。所以检索、相关推荐和上下文召回，才是知识管理系统真正关键的部分。

### C2

我现在判断一个笔记系统好不好，不是看编辑器功能有多强，而是看旧内容能不能被重新用起来。当我写一条新笔记时，系统如果能把过去相关的想法主动拉出来，就会大幅降低重复思考。

这其实是在把“存储系统”升级成“思考辅助系统”。所以相关推荐功能对笔记产品来说不是锦上添花，而是核心能力。

### C3

知识型笔记很容易出现同义表达、抽象表达和不固定措辞。如果只靠关键词检索，很多相关内容其实找不回来。

语义检索的价值在于，即使表述不同，也能识别背后的主题接近性。对长期积累型笔记系统来说，这种能力比传统搜索更重要。

### D1

最近我开始重新规划自己的锻炼安排，重点放在力量训练和恢复节奏上。以前我总觉得训练只是维持状态，但现在更关注长期体能、专注力和稳定作息之间的关系。

身体状态一旦更稳定，工作时的耐力和判断力也会更好。所以健身对我来说不只是身体目标，也是工作状态管理的一部分。

### D2

最近在看显示器时，我发现自己最在意的并不是分辨率，而是长时间使用时的舒适度。包括亮度、色温、支架调节、接口稳定性和桌面空间占用。

真正高频使用的设备，体验差异往往体现在这些细节上。对工作设备来说，长期舒适度比参数表更重要。

### D3

技术负责人不仅要保证代码质量，还要建立稳定的发布节奏。这包括灰度发布、回滚预案、上线检查和事故响应机制。

如果上线流程经常靠个人经验驱动，团队就会越来越脆弱。稳定发布能力，是工程管理成熟度的重要体现。
